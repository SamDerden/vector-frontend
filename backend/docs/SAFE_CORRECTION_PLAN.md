# План безопасной коррекции

План не выполняется на рабочей базе, Railway и общем сервере. Новых миграций этот пакет не добавляет. Уже применённые файлы `001`–`011` не переписываются.

Порядок ниже идёт от действий без изменения данных к действиям, которые требуют отдельного решения. Шаг нельзя начинать, пока не закрыт его пункт «подтвердить до изменения».

## Действия без миграции и без записи в рабочую базу

### DB-01. Пустой `graph_profession_id` у всех импортированных профессий

- Факт. На стенде 30/30 профессий имеют `external_id` и `graph_profession_id IS NULL`. Загрузчик этот столбец не пишет. `mapCatalogProfessionId` даёт `unmapped`.
- Затронуто. `professions.graph_profession_id`, адаптер Софи, ключ маршрута.
- Влияние. Названия и `retrieval_only` работают. Отдельный UUID профессии не появляется. Потери строк нет.
- Приоритет. P0 для маршрута по профессии. P2 для самой генерации текста.
- Исправление. Не заполнять столбец вычисленным UUID. Когда Алиса подтвердит соответствие, значением должен быть исходный id каталога, например `prof_004`, и только если этот id есть в графе. Запись — отдельный согласованный прогон загрузчика на копии, не `UPDATE` по догадке.
- Миграция. Не нужна: колонка уже есть в `005_hybrid_professions.sql`.
- Подтвердить. Список пар «id графа → существующая строка» от Алисы. Илона подтверждает, что до этого один маршрут на сессию допустим.
- Backup и dry-run. Дамп только той базы, которую разрешат менять. Сначала `SELECT external_id, graph_profession_id FROM professions ORDER BY external_id` без вывода описаний учеников. На стенде повторно загрузчик не запускать, пока нет утверждённого соответствия.
- Проверка после. Число строк с непустым `graph_profession_id` равно числу утверждённых пар. Уникальный индекс не нарушен. Рекомендация получает UUID, а маршрут перестаёт схлопываться в `none` только для этих пар.
- Откат. Вернуть прежние NULL из дампа колонки. Схему не удалять.
- Согласование. Алиса — источник id. Илона — продукт маршрута. Backend не записывает соответствие сам.
- Уже можно локально. Оставить столбец пустым. Это текущее состояние стенда.

### DB-02. `professionKey = none` для не-UUID

- Факт. `app/page.tsx` подставляет `none`, если id не UUID. На стенде 3/3 маршрута имеют ключ `none`.
- Затронуто. `education_routes`, `GET/PUT /api/education-route`.
- Влияние. Программы разных профессий одной сессии делят одну серверную строку. Версия и 409 относятся к этому общему ключу. Данные других сессий не затрагиваются.
- Приоритет. P0, следствие DB-01.
- Исправление. После появления настоящих UUID профессий клиент начнёт слать UUID без смены контракта: ключ уже принимает UUID. До этого контракт не менять и ключи в базе не переписывать.
- Миграция. Нет.
- Подтвердить. Решение Илоны: ждать id или осознанно жить с одним маршрутом на сессию.
- Backup. Не требуется, пока строки не обновляются.
- Проверка. Для UUID-ключа две профессии одной сессии дают две строки. Для `none` 409 по версии сохраняется.
- Откат. Не требуется, если записи не менялись.
- Согласование. Илона.
- Уже можно локально. Ничего не менять в интерфейсе.

### DB-03. Пустая `vacancy_snapshots`

- Факт. В графе объявлено 30 снимков. Таблица стенда пуста. Загрузчик в неё не пишет. `professions.vacancies_count` заполнен у всех 30.
- Затронуто. Таблица `vacancy_snapshots`. Генерация читает число из профессии и JSON.
- Влияние. Потери пользовательских данных нет. Исторических снимков в этой таблице нет.
- Приоритет. P2.
- Исправление. Не создавать загрузчик в этом проходе. Если продукт захочет таблицу, нужен отдельный согласованный импорт из графа.
- Миграция. Нет, таблица уже создана ранней схемой.
- Подтвердить. Нужна ли Алисе и Илоне отдельная таблица, если число уже лежит в `professions`.
- Backup. Дамп перед любым будущим импортом.
- Проверка. `count(*)` равен утверждённому числу, сирот по `profession_id` нет.
- Откат. Удаление только строк этого импорта, не всего каталога.
- Согласование. Алиса и Илона.
- Уже можно локально. Зафиксировать расхождение. Импорт не запускать.

### SES-01. Ownership уже включён кодом production

- Факт. `sessionProofEnforced` истинен при `NODE_ENV=production` даже без `SESSION_PROOF_ENFORCED`. Cookie не перевыпускается для существующей строки.
- Затронуто. `POST /api/track/select` и все маршруты, зовущие `authorizeSessionOwnership`.
- Влияние. Старый UUID без cookie получает 403. Сессия и ответы не удаляются.
- Приоритет. P0 перед выкладкой этой ветки.
- Исправление. Конфиг и проверка браузера, не новая миграция. Секрет длиннее 32 байт. Браузер ходит на тот же origin. У текущих сессий уже есть cookie, либо Илона принимает, что старые локаторы без cookie начнут новую сессию. Флаг отдельно не включать.
- Миграция. Нет. 009 не обязана заполнять старые `expires_at`.
- Подтвердить. Администратор снимает read-only health: `sessionOwnership`. Илона подтверждает same-origin и судьбу старых сессий.
- Backup. Дамп `sessions` без колонок ответов, только id, mode, expires_at, до любой чистки.
- Dry-run. На копии: сессия без cookie → 403; новая сессия → cookie HttpOnly, SameSite=Strict; чужая сессия → 403; NULL `expires_at` не попадает в cleanup.
- Проверка. Playwright-набор стенда: cookie, 403, 410, 409. На сервере один свой тестовый профиль, не ученический.
- Откат. Вернуть предыдущий артефакт API. Секрет и строки сессий не удалять.
- Согласование. Илона и администратор.
- Уже можно локально. Стенд с `SESSION_PROOF_ENFORCED=true` это уже покрывает. На сервере не включать.

### SES-02. Подмена `X-Forwarded-For`

- Факт. Первый адрес заголовка выбирает in-memory bucket и IP-бюджет выбора трека. Unit-тест показывает смену bucket при смене первого адреса.
- Затронуто. `abuse-guard.ts`, `sessions:ip:*`, лимит 180/10 мин.
- Влияние. Без доверенного proxy лимит обходится. С общим школьным NAT честные ученики делят один счётчик и могут получить 429. Данные не пропадают.
- Приоритет. P1.
- Исправление. Не менять алгоритм, пока неизвестен proxy. После схемы сети брать адрес только от доверенного hop. Произвольный внешний заголовок не считать клиентом.
- Миграция. Нет.
- Подтвердить. Администратор: кто выставляет `X-Forwarded-For` и переписывается ли он на границе.
- Backup. Не требуется для чтения конфигурации.
- Dry-run. На копии два запроса с разными первыми адресами и один общий второй. Ожидание фиксируется до правки кода.
- Проверка. После правки подмена первого адреса не меняет bucket, а адрес от доверенного proxy меняет.
- Откат. Вернуть прежний разбор заголовка одним коммитом.
- Согласование. Администратор. Backend не меняет формулу вслепую.
- Уже можно локально. Тест и этот документ. Код лимита не менять.

### SES-03. NAT и общий IP

- Факт. Выбор трека: 30 запросов в минуту на IP-bucket и 180 за 10 минут в памяти процесса. Генерация ограничена сессией и глобальным счётчиком, не этим NAT-счётчиком.
- Затронуто. `POST /api/track/select`, `request_budgets`.
- Влияние. Школа за одним адресом может временно не открывать новые треки. Уже открытые сессии остаются.
- Приоритет. P1.
- Исправление. Сначала измерить read-only `used` ключей `sessions:ip:%` и `sessions:global` за окно. Порог менять только после цифр и согласия Илоны.
- Миграция. Нет.
- Подтвердить. Администратор снимает агрегаты. Илона решает, приемлем ли порог.
- Backup. Не требуется для `SELECT`.
- Откат. Вернуть числа 30/60 и 180/10 в конфиге процесса.
- Согласование. Илона и администратор.
- Уже можно локально. Стендовый тест 180 уже зелёный. Порог не менять.

### SES-04. Cookie и другой origin

- Факт. `Domain` не задан. `lib/api.ts` не ставит `credentials: "include"`. Same-origin proxy с пустым `NEXT_PUBLIC_API_BASE_URL` cookie отправляет. Другой API-host — нет.
- Затронуто. Выдача proof и все защищённые POST/GET.
- Влияние. После смены хоста или при отдельном API-host проверка даёт 403. Ответы в базе остаются.
- Приоритет. P1, если публичный API-base не пуст. Иначе риск только при будущей смене origin.
- Исправление. Держать браузер и API на одном origin через rewrite. Не ставить широкий `Domain`. Не класть proof в localStorage.
- Миграция. Нет.
- Подтвердить. Администратор: фактические `BACKEND_INTERNAL_URL` и `NEXT_PUBLIC_API_BASE_URL` без вывода секретов.
- Проверка. Запрос с cookie на тот же origin → 200. `credentials: omit` → 403. Это уже есть в Playwright стенда.
- Откат. Вернуть пустой публичный API-base.
- Согласование. Администратор и Илона.
- Уже можно локально. Не менять frontend.

### QUE-01. Публичный 502 не подтверждён

- Факт. Локально отвязанный `insertClient.query` давал 502 `persist_failed` после успешного fallback. Исправление в `68a9ae1`: метод вызывается со своим клиентом. Стенд на `3b49aa9` снова фиксирует один commit и replay. Логи сервера не снимались.
- Затронуто. `recommendations`, `generation_jobs`, `POST /api/recommendations/generate`.
- Влияние. Если на сервере ещё старый код, сохранение могло откатываться. Если ревизия уже содержит исправление, причина часа недоступности другая: 403/503 ownership, 429 бюджета или обрыв proxy.
- Приоритет. P0 для диагноза, не для новой правки кода.
- Исправление. Сначала три read-only показателя из `READONLY_ADMIN_CHECKS.sql` и health. Код повторно не переписывать, пока ревизия не показала старый `sofi-generate.ts`.
- Миграция. Нет.
- Подтвердить. Администратор: `revision`, доли `httpStatus`/`errorCode`, статусы задач за час.
- Backup. Не требуется для чтения.
- Проверка после выкладки уже готового коммита. Новый синтетический ключ даёт одну рекомендацию. Повтор не создаёт вторую и не пишет второй вызов модели.
- Откат. Предыдущий артефакт API. Строки рекомендаций не удалять.
- Согласование. Администратор снимает цифры. Backend уже отдал исправление в ветке.
- Уже можно локально. Считать локальный дефект закрытым. Сервер не объявлять исправленным.

### QUE-02. Worker не входит в обычный старт

- Факт. Новый ключ считается внутри API. Истёкшая аренда ждёт отдельный процесс. Команда `npm run worker:generation` использует боевой `DATABASE_URL` и живой пайплайн.
- Затронуто. `generation_jobs.locked_until`, процесс worker.
- Влияние. Обрыв на 3 минуты оставляет задачу `running`, пока нет worker. Повтор того же ключа не создаёт вторую генерацию. Другая сессия работает.
- Приоритет. P1.
- Исправление. Отдельный процесс с тем же артефактом и той же базой, что API. Не направлять команду на `navigator-postgres` и не включать живой AI, пока шлюз не согласован.
- Миграция. Нет.
- Подтвердить. Администратор: запущен ли процесс и что health `generationWorker` означает в их окружении.
- Backup. Дамп `generation_jobs` по статусам, без `input_snapshot`.
- Dry-run. На копии: живая аренда не забирается, истёкшая без рекомендации доходит до попыток, уже сохранённая присоединяется.
- Откат. Остановить процесс. Строки не чистить.
- Согласование. Администратор.
- Уже можно локально. Стендовый stub-worker. Боевую команду не запускать.

### QUE-03. Бюджет повторного POST

- Факт. Код `generationBudgetApplies` списывает бюджет только для отсутствующей или `failed` задачи. Unit-контракт проверяет исходный текст маршрута. Отдельный `SELECT used` до и после HTTP-replay на стенде не снимался.
- Затронуто. `request_budgets`, ключи `generate:global` и `generate:session:*`.
- Влияние. Ошибочное двойное списание дало бы лишний 429, не потерю рекомендации.
- Приоритет. P2, пробел доказательства.
- Исправление. Добавить стендовый тест HTTP-replay и сравнить `used`. Контракт API не менять, если тест подтвердит текущий код.
- Миграция. Нет.
- Подтвердить. Ничего на сервере. Это локальный тест.
- Откат. Удалить тест, если он нестабилен.
- Согласование. Backend.
- Уже можно локально. Следующим отдельным коммитом, не в этом аудите: аудит не меняет поведение.

### SAV-01. Рефлексия интерфейса не пишет `journeyStep`

- Факт. `PrimaryExperience.tsx` отправляет `rating` и `comment`. `journeyStep` и `stage` не отправляет. API умеет сохранить шаг. На стенде 7/7 рефлексий имеют NULL в `journey_step`.
- Затронуто. `reflections.journey_step`, `POST/GET /api/reflection`.
- Влияние. Финальный дневник сохраняется как оценка и комментарий. Серверный шаг путешествия остаётся пустым. Старые строки совместимы: NULL разрешён.
- Приоритет. P1 для продукта шага, P2 для сохранности текста.
- Исправление. Илона решает, должен ли клиент слать `journeyStep` 1…4 и `stage: "final"` на последнем экране. Backend поля уже принимает. Интерфейс в этом плане не переписывается. Существующие NULL не обновлять массово.
- Миграция. Нет.
- Подтвердить. Илона: нужен ли серверный шаг для уже нарисованных четырёх этапов.
- Backup. Перед любой будущей простановкой шагов — дамп `reflections` без текста комментария, только id и `journey_step`.
- Проверка. POST с шагом 4 возвращает `journeyStep: 4` и `stage: final`. POST без шага по-прежнему сохраняет текст и оставляет NULL.
- Откат. Клиент перестаёт слать поле. Записанные шаги можно оставить.
- Согласование. Илона.
- Уже можно локально. Не менять UI. Контракт описан здесь.

### SAV-02. Частичная запись рекомендации

- Факт. Текущий INSERT и завершение задачи — одна транзакция. На стенде нет завершённой задачи без рекомендации и нет рекомендации без задачи среди текущих 21 строк. Worker умеет присоединить разорванную пару.
- Затронуто. `recommendations`, `generation_jobs`.
- Влияние. При сбое текущий код откатывает обе стороны. Пользователь видит 502 `persist_failed`, повтор не создаёт дубль.
- Приоритет. P2, наблюдение. Отдельная коррекция не требуется.
- Исправление. Не чинить вслепую. Если read-only SQL на разрешённой базе покажет `completed` без рекомендации или рекомендацию без завершённой задачи, сначала сохранить id пар и только потом запускать уже существующий attach worker на копии.
- Миграция. Нет.
- Согласование. Администратор приносит агрегаты. Backend смотрит их до любого `UPDATE`.
- Уже можно локально. Считать текущий транзакционный путь подтверждённым стендом.

## Действия, которые требуют отдельного разрешения

1. Любой `INSERT`/`UPDATE` каталога на базе кроме изолированного стенда, включая заполнение `graph_profession_id`.
2. Повторный запуск `sync-hybrid-catalog.mjs` против рабочей базы.
3. `cleanup-expired-sessions.mjs --apply` где бы то ни было, кроме будущей копии. NULL `expires_at` не удалять.
4. Применение 007–011 на рабочей базе. На стенде они уже есть. На рабочей — только после дампа и явного разрешения. Номер файла `010_request_budgets.sql` не переименовывать.
5. Запуск `npm run worker:generation` с боевым `DATABASE_URL` или живым AI.
6. Включение `SESSION_PROOF_ENFORCED` на общем окружении.
7. Смена порогов NAT и разбора `X-Forwarded-For`.
8. Выкладка ветки. Локальный код к этому плану готов только как кандидат. Сервер этим планом не обновляется.

## Общий порядок

1. Администратор выполняет `backend/docs/READONLY_ADMIN_CHECKS.sql` на той базе, которую ему отдельно разрешат. Результат — только счётчики и имена файлов миграций.
2. По ревизии health решить, нужен ли уже готовый фикс `persist_failed`, или час недоступности объясняется 403, 429 либо отсутствием worker.
3. Илона подтверждает same-origin и судьбу старых сессий до выкладки ownership.
4. Алиса и Илона подтверждают пары `graph_profession_id` до любой записи. До этого маршрутный ключ остаётся `none`.
5. Илона решает, слать ли `journeyStep` из дневника. Backend поле уже хранит.
6. Администратор описывает proxy. До этого формула `X-Forwarded-For` не меняется.
7. Worker поднимается отдельным процессом только после дампа и только на согласованной базе.
8. Откат любого из этих шагов — предыдущий артефакт и остановка worker. Колонки 007–011 и ответы учеников не удалять.
