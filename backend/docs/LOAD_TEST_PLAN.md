# Нагрузочный сценарий для отдельного стенда

Это план, а не результат прогона. Ниже стартовые параметры как гипотеза. Измеренных значений этот прогон не содержит: общий сервер, рабочая PostgreSQL и AI-шлюз не использовались.

## Гипотеза старта

| Параметр | Гипотеза | Зачем смотреть |
|---|---|---|
| Класс | 30 учеников одновременно | Обычный школьный сценарий |
| Четыре класса | 120 учеников | Верхняя гипотеза одного стенда |
| Повтор генерации | тот же Idempotency-Key, 3 раза | Не должен создавать вторую задачу |
| Пауза опроса | 2 секунды, не чаще лимита чтения 240/мин | Ожидается 202, затем 201 |
| Пул PostgreSQL | сейчас по умолчанию 10, потолок кода 20 через `DATABASE_POOL_MAX` | Очередь подключений |
| Worker | один отдельный процесс | Очередь `generation_jobs` |
| AI | отдельная тестовая квота, не боевой ключ | Таймауты и 502 |

Целевые ориентиры, их ещё нужно измерить на стенде: health до 200 мс, чтение каталога до 500 мс, приём генерации (202 или 201 без ожидания модели) до 300 мс. Полная генерация зависит от шлюза и в эту гипотезу не входит.

## Что снимать

- CPU и RAM процесса API и процесса worker.
- Число подключений PostgreSQL и ожидание клиента.
- Длину очереди: `pending`, `running`, `failed` в `generation_jobs`.
- Долю 201, 202, 429, 502 и время до сохранения рекомендации.
- Расход квоты AI. На стенде задать отдельный ключ и маленький лимит.
- Логи: только `event`, `requestId`, `httpStatus`, `errorCode`, `durationMs`. Ответов ученика и секретов в логах быть не должно.

## Как не вредить

Запускать только на пустой или специально созданной базе стенда. Не направлять сценарий на общий сервер и не повышать `DATABASE_POOL_MAX` на рабочей базе без отдельного решения: на ней уже есть другие сервисы. Сценарий не запускался в этом изменении.
